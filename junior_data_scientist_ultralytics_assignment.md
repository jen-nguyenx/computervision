## 1. Purpose of the Assignment

This assignment evaluates whether you can take an ambiguous computer-vision request and turn it into a reliable, reproducible, and clearly explained solution.

You will use **Ultralytics** to build three computer-vision pipelines:

1. Axis-aligned object detection using bounding boxes.
2. Oriented object detection using oriented bounding boxes.
3. Instance segmentation using object masks.

The primary goal is **not** to achieve the highest possible accuracy. We are evaluating how you:

- Decompose a vague and complex problem into smaller tasks.
- Use Claude, GPT, or another comparable language model to analyse each workstream and propose an initial solution.
- Turn AI-assisted drafts into working training and deployment code.
- Critically review, test, correct, and sometimes reject AI-generated answers.
- Evaluate models using appropriate metrics and error analysis.
- Communicate your results, limitations, and recommendations.

You remain fully responsible for the correctness of everything you submit, including any content or code initially generated by AI.

## 3. Dataset Scope and Annotation Semantics

This assignment uses two public datasets and three model tasks.

### 3.1 COCO 2017 Train Subset: `COCO5K`

Use the first 5,000 images from the official **COCO 2017 train split**.

The official COCO instance annotations provide:

- Axis-aligned bounding boxes.
- Per-instance segmentation for non-crowd objects, usually represented as polygons.
- Encoded mask regions for some annotations, including crowd regions.

COCO does **not** provide native oriented bounding-box labels for this assignment.

You will use the same COCO5K subset to train:

- One Ultralytics detection model.
- One Ultralytics instance-segmentation model.

### 3.2 DOTA v1.0 Train Subset: `DOTA5K`

DOTA v1.0 does not contain 5,000 original training images. Its original images are high resolution and are normally divided into smaller training patches.

For this assignment, **DOTA5K means the first 5,000 generated image patches**, not 5,000 original source images.

The official DOTA v1.0 annotations provide:

- Four-corner quadrilateral annotations representing oriented objects.
- A class label.
- A difficulty field.

An axis-aligned bounding box can be derived from a DOTA quadrilateral, but DOTA quadrilaterals are **not true object-shape instance masks**. Do not describe a DOTA quadrilateral as a ground-truth segmentation mask.

You will use DOTA5K to train:

- One Ultralytics OBB model.

### 3.3 Required Models

Your final submission must contain three trained and evaluated models:

| Model ID | Dataset | Ultralytics Task | Required Geometry |
|---|---|---|---|
| `coco5k-detect` | COCO5K | Detection | Axis-aligned bounding box |
| `coco5k-segment` | COCO5K | Instance segmentation | Instance mask or polygon |
| `dota5k-obb` | DOTA5K | Oriented detection | Four-point oriented box |

Do not compare the absolute accuracy of COCO and DOTA models as if they were solving the same problem. They use different domains, classes, geometries, and label semantics.

## 4. Deterministic Dataset Construction

Your dataset preparation must be scripted and reproducible. Do not select files using unspecified filesystem order.

### 4.1 Constructing COCO5K

Use:

```text
train2017/
annotations/instances_train2017.json
```

Construct COCO5K as follows:

1. Load the `images` entries from `instances_train2017.json`.
2. Sort them by numeric COCO image ID in ascending order.
3. Select the first 5,000 image records.
4. Retain every selected image, including any image with no usable instances.
5. Retain only annotations whose `image_id` belongs to the selected 5,000 images.
6. Preserve the original COCO category IDs in the source subset and create an explicit mapping to contiguous Ultralytics class IDs.
7. Save a deterministic manifest containing at least:

```text
image_id
file_name
width
height
source_split
```

The same COCO train, validation, and test manifests must be used for both the detection and segmentation models.

### 4.2 Constructing DOTA5K

Use the labeled original images from the official **DOTA v1.0 train split**.

Generate training patches with the following settings:

```text
Patch size: 1024 × 1024
Gap/overlap setting: 200 pixels
Scale rates: [1.0]
```

You may use the official DOTA Devkit, the Ultralytics DOTA conversion and splitting utilities, or your own verified implementation. Pin the exact tool version or Git commit used because patching and boundary-handling behaviour can change between implementations.

After patch generation:

1. Sort generated patch basenames lexicographically.
2. Select the first 5,000 patches.
3. Retain background patches unless you provide and justify a different policy.
4. Create a manifest containing at least:

```text
patch_file_name
source_image_id
patch_x
patch_y
patch_width
patch_height
instance_count
```

The mapping between each patch and its original DOTA image must be preserved. Multiple patches from the same source image are strongly correlated and must not be split across dataset partitions without explicit justification.

### 4.3 Dataset Integrity

Do not manually edit individual label files or images.

Any exclusion, correction, clipping operation, category remapping, or unsupported annotation must be:

- Implemented in code.
- Counted.
- Logged.
- Explained in the final report.

Do not commit raw COCO or DOTA images to your Git repository. Commit scripts, manifests, configurations, summaries, and representative visualisations only.

### 9.2 Pretraining and Leakage Policy

Be careful when selecting initial weights:

- Standard Ultralytics detection and segmentation checkpoints may already have been trained on COCO.
- Standard Ultralytics OBB checkpoints may already have been trained on DOTA.

For your principal scored baselines, do not claim independent generalisation results if the initial checkpoint was trained on images contained in your validation or test partitions.

Use one of the following defensible approaches:

- Train the selected architecture from scratch.
- Use weights whose pretraining dataset is demonstrably disjoint from the evaluated images.
- Run a contaminated transfer-learning experiment only as a clearly labelled secondary experiment, not as the main held-out result.

Document the source and expected data lineage of every starting checkpoint.

### 14.6 Communication and Reporting
