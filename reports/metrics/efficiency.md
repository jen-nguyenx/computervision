# Inference efficiency benchmark (§10.7)

Generated by `src/evaluate/benchmark.py`. Dedicated benchmark — these numbers replace the in-pass latency in `slices_val.json`, which had no warm-up.

- hardware: **Apple M5 Pro, 64 GB, MPS backend** (detected: Apple M5 Pro, 64 GB, macOS-26.5.2-arm64-arm-64bit)
- torch 2.13.0 · ultralytics 8.4.117 · device `mps` · batch size 1 · precision fp32
- fixed input: val image id **30** (`000000000030.jpg`, 640x428) — one image for every sample and both models, so object count and NMS load are constant
- per call: conf 0.001, NMS IoU 0.7, max_det 300 (the mAP-protocol settings, so the comparison with the in-pass figures is like for like)
- protocol: at least 20 discarded warm-up inferences *and* at least 1.0 s of them (per-model counts in the table below), then at least 100 measured *and* at least 1.5 s of them — and that whole block repeated 5 times; `torch.mps.synchronize()` before every clock read because MPS dispatch is asynchronous
- latency is end-to-end per image: read + letterbox preprocess + forward + NMS + postprocess

## Steady-state latency (batch 1, single image)

| model | imgsz | median ms | P95 ms | mean ms | std ms | throughput img/s | n warm-up | n measured |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 640 | 640 | 6.55 | 9.56 | 6.87 | 1.13 | 145.6 | 145 | 219 |
| 960 | 960 | 8.04 | 8.52 | 8.07 | 0.24 | 124.0 | 127 | 186 |

- 640: 5 repeated blocks with medians 6.82, 6.55, 6.80, 6.55, 7.02 ms (5 discarded as drifted); the reported block has first/middle/last-third medians of 6.70, 6.18, 6.67 ms, a spread of 7.9% of its median.
- 960: 5 repeated blocks with medians 8.04, 8.06, 8.11, 8.45, 8.27 ms (1 discarded as drifted); the reported block has first/middle/last-third medians of 8.06, 8.02, 8.03 ms, a spread of 0.4% of its median.

Measurement caveat: this is a laptop whose GPU is shared with the macOS window compositor, so any block can be slowed by unrelated desktop activity. The whole block is therefore repeated 5 times; blocks that drift mid-run (thirds disagreeing by more than 5% of the median) are discarded, and the fastest of the survivors is reported, because contention is additive and can only ever slow a block down. Every attempt's median is listed above so the run-to-run spread is visible.

## Model size, load cost and training cost

| model | params | checkpoint MB | precision | load: construct ms | load: first inference ms | cold start ms | training duration | peak GPU mem |
|---|---:|---:|---|---:|---:|---:|---|---|
| 640 | 2,624,080 | 5.30 | fp32 | 36.0 | 630.7 | 666.7 | 45 min (2707 s) — **early-stopped at epoch 269**, best epoch 169 | 6.52 GB |
| 960 | 2,624,080 | 5.35 | fp32 | 48.9 | 157.9 | 206.8 | 110 min (6581 s) — ran the full 300 epochs, best epoch 217, early stopping never triggered | not recorded (no 'peak gpu memory' row in run_records.md) |

Parameter counts are the as-trained figures (matching `run_records.md`). Ultralytics fuses Conv+BatchNorm on the first inference, so the count actually executing is slightly lower — see `parameters_fused_for_inference` in `efficiency.json`. Checkpoint size is MiB (1024^2 bytes) of the `best.pt` file.

Cold start is measured with the MPS device context already created, so it is not charged to whichever model is benchmarked first. Metal's compiled-kernel cache is still process-wide: a model loaded second in the same process reuses some of those kernels and its `first inference` column is therefore a lower bound on a genuinely cold process.

Training duration and peak GPU memory are transcribed from `reports/metrics/run_records.md` and were measured on the **training** machine (RunPod RTX 4090 24 GB), not on the Apple Silicon machine used for the latency columns. The two are not comparable. `not recorded` means the value is absent from the run record — it has not been estimated.

## Effect of warm-up: in-pass figures vs this benchmark

| model | in-pass median ms | steady median ms | change | in-pass P95 ms | steady P95 ms | change |
|---|---:|---:|---:|---:|---:|---:|
| 640 | 14.54 | 6.55 | -55.0% | 28.72 | 9.56 | -66.7% |
| 960 | 17.48 | 8.04 | -54.0% | 162.19 | 8.52 | -94.7% |

- `run_records.md` quotes **15.7 ms** as the median latency for model 640; that is the same contaminated in-pass measurement and should be superseded by the steady-state column above.
- `run_records.md` quotes **18.6 ms (+18% vs 640, far less than the +125% pixel count)** as the median latency for model 960; that is the same contaminated in-pass measurement and should be superseded by the steady-state column above.

The in-pass columns come from `slices_val.json`: measured inside the mAP loop with no warm-up, no device synchronisation, and a different image on every call. Two separate effects are collapsed in that number — the uncompiled first call, and a fresh letterbox shape per image forcing repeated Metal graph builds. Neither is steady state, so only the columns in this file should be quoted as inference latency.
